### PROBLEM

The production hero renderer uses two different coordinate policies for RIGHT and LEFT. The sprite destination rectangle is snapped with `Math.round(...)`, but LEFT is produced by mirroring the canvas around the unsnapped floating-point physics coordinate `p.x`. This makes the final rendered center depend on facing direction. At a hard RIGHT↔LEFT reversal, the physical player can remain at exactly the same x while the visible body moves horizontally because the mirror pivot and raster destination are not the same anchor.

This is separate from cadence, foot planting, camera look-ahead and the slow-WALK 60/90/120 Hz distance-loss issue. It is a presentation-space symmetry problem in `engine-ab.js`.

### CONFIRMED_IN_GEMINI

At base commit `38eb8277...` / visible build V6.00:

1. `engine-ab.js` is still the production PNG hero override despite `ENGINE_MAP.md` still naming `engine-m.js` as hero owner. The map is stale for this responsibility.
2. Lateral destination width is `dw=48`; the body destination X is `Math.round(p.x - dw/2)`. Since `dw/2=24`, the unmirrored RIGHT sprite center is effectively `Math.round(p.x)`.
3. LEFT executes `ctx.translate(p.x,0); ctx.scale(-1,1); ctx.translate(-p.x,0)` using the unsnapped floating `p.x`, then draws the same already-rounded destination rectangle.
4. Therefore, if `R=Math.round(p.x)`, RIGHT visual center is `R`, while LEFT visual center after the mirror is `2*p.x - R`.
5. The RIGHT-vs-LEFT center difference at identical physics x is therefore `2*(R-p.x)` in magnitude, which can approach 1.0 world px and is exactly 1.0 world px at half-pixel positions under JavaScript `Math.round` behavior.
6. The nameplate is always drawn at `Math.round(p.x)`. It aligns with the snapped RIGHT body center, but LEFT can be offset from it by the same `2*(R-p.x)` amount. Thus this is not only a reversal pop; LEFT can have a small body/name anchor mismatch that RIGHT does not.
7. `engine-z.js` currently allows `CONFIG.zoom` from 1.05 to 1.45. A 1.0-world-px body-center discrepancy therefore becomes up to ~1.45 CSS px before considering DPR backing resolution.
8. `engine-l.js` uses a HiDPI backing store up to DPR 3. The same ~1.45 CSS-px discrepancy can span ~4.35 backing pixels at DPR 3. DPR does not enlarge the CSS displacement, but it changes which physical samples are hit and can make asymmetrical nearest-neighbor sampling/shimmer more visible.
9. `engine-ab.js` disables `imageSmoothingEnabled` for hero draw, but nearest-neighbor does not make a fractional transform identical to an integer-aligned transform; the current LEFT transform can still place the raster on a different sampling phase than RIGHT.
10. Source cropping is also fractional (`padX=FW*0.05`, `padY=FH*0.04`, currently roughly 12.8 and 15.36 for the expected sheet geometry). That is a separate sampling concern and should NOT be changed in the same experiment.
11. `engine-ac.js` already stores update-side visual facing/frame and should remain the locomotion-state owner. This round does not propose advancing state during render.
12. `engine-ah.js` remains a hard-stop wrapper; no change to that wrapper is needed for this experiment.

### EXTERNAL_EVIDENCE

1. MDN Canvas 2D transformation documentation confirms `translate()` and `scale()` modify the current transformation matrix and that negative scale mirrors the coordinate system. Therefore an unsnapped `p.x` used as the mirror origin mathematically participates in the final raster position.
2. MDN documents that `drawImage()` destination position/size are transformed by the active Canvas 2D transform and that scaling is permitted with real-valued transforms.
3. MDN documents `imageSmoothingEnabled=false` as disabling smoothing when images are scaled. It does not establish a guarantee that arbitrary fractional source/destination/transform combinations become pixel-aligned or symmetric.
4. Godot issue #57221 documents a closely related class of pixel-art instability where float motion combined with transforms can cause visible pixel jitter. It is not proof of the exact Kelo bug, but supports benchmarking transform/sample phase rather than assuming nearest-neighbor alone solves it.
5. Recent Godot/Raylib community reports likewise describe visible jitter when float movement, camera transforms, nearest filtering and non-integer scaling interact. Counterevidence from those discussions is important: indiscriminately snapping every world coordinate can make motion itself look stair-stepped, so the fix should target the inconsistent LEFT/RIGHT anchor first instead of globally integer-quantizing physics or camera.

### HYPOTHESIS

The current asymmetric anchor contributes a small but repeatable visual pop during lateral reversal and can add LEFT-only shimmer/nameplate misalignment. A minimal presentation-only change that uses one canonical snapped visual center for both the destination rectangle and the LEFT mirror pivot should remove the direction-dependent center shift while preserving current RIGHT rendering, physics, collider, stride, speed and camera.

This does NOT prove that integer world snapping is the final best sampling policy. It only predicts that using inconsistent anchors is worse than using one shared anchor.

### PROPOSED_CHANGE

Benchmark before production selection:

**A — Baseline current behavior**
- destination center effectively `Math.round(p.x)`;
- LEFT mirror pivot uses raw `p.x`.

**B — Minimal symmetric snapped-anchor candidate (preferred first test)**
- define `drawCx=Math.round(p.x)` once;
- destination X uses `drawCx-dw/2`;
- LEFT mirror around `drawCx`, not raw `p.x`;
- nameplate X also uses the same `drawCx`;
- keep footY/Y policy, source crop, image smoothing, zoom, collider and camera unchanged.

This preserves current RIGHT placement exactly while changing only LEFT anchor math.

**C — Continuous unsnapped visual-anchor candidate (benchmark only, not first production recommendation)**
- use raw `p.x` consistently for destination center and mirror pivot;
- do not round body X in world space;
- keep nameplate decision separate or align to same presentation anchor for the test.

Candidate C may produce smoother world-space motion but could increase nearest-neighbor shimmer under fractional zoom/camera, so it must not be assumed superior.

Do NOT combine this experiment with source crop rounding, avatar scale changes, cadence fixes, foot settle, shadow, bob, lean, camera dead-zone changes or render-pass refactors.

### DO_NOT_ASSUME

- Do not assume the ~1 world px worst-case shift is always perceptible; measure screenshots/rects around reversal.
- Do not globally snap `localPlayer.x`, camera x or collision positions. Physics must remain floating point.
- Do not claim `imageSmoothingEnabled=false` guarantees pixel-perfect output under fractional transforms.
- Do not modify `padX/padY` in the same change even though they are fractional; that would mix source-sampling and anchor experiments.
- Do not enlarge Kelo in this experiment. Scaling would amplify the visual stakes and confound comparison.
- Do not treat DPR backing-pixel counts as CSS movement distance; report both separately.

### EXPERIMENT

Use the standard deterministic lateral trace with an additional controlled fractional-position matrix.

1. Record baseline commit and V6.00 build identity.
2. Instrument hero presentation only with per-draw values: `physicsX`, `drawCx`, `face`, `destXBeforeTransform`, effective `visualCenterWorldX`, nameplateX, `CONFIG.zoom`, DPR and current CTM from `ctx.getTransform()`.
3. Place or move Kelo through representative fractional x residues near: `.00`, `.10`, `.25`, `.49`, `.50`, `.51`, `.75`, `.90` while y is fixed in an unobstructed area.
4. At each residue, render RIGHT and LEFT without changing physical x. Capture the effective body center and a clipped screenshot.
5. Run hard RIGHT→LEFT and LEFT→RIGHT reversals under normal movement at representative mobile/desktop viewports.
6. Repeat at zoom ~1.05, ~1.25 and ~1.45 where reachable, and DPR 1/2/3 in the pinned browser harness.
7. Compare A vs B using the exact same world/camera traces.
8. Only if B fixes symmetry but still shows unacceptable whole-body shimmer, test C as a separate candidate.
9. Keep `localPlayer.radius=20`, world position trace, gait, stridePhase and camera trace identical between A/B.

### RISKS

- B can remove the reversal asymmetry but retain normal pixel-step motion because RIGHT already uses integer world snapping. That is acceptable for this isolated test but not proof of final sampling quality.
- C can look smoother at one zoom and worse at another because non-integer zoom and DPR change sample phase.
- Duplicate actor rasterization or later depth redraws can contaminate screenshot measurements; tag render pass/draw count if current runtime invokes `renderAvatar` multiple times.
- The current 4-frame sprite and fractional source crop can dominate perceived edge shimmer, hiding or exaggerating the anchor effect.
- If camera movement changes between comparison traces, a screenshot-only judgment can misattribute camera sampling to body anchor. Record CTM/camera state.
